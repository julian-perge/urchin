# Driving the game without taking over the real mouse and keyboard

Date: 2026-11-08. Julian asked whether the Godot instance can run on a separate macOS screen, or whether the window has to have focus for the godot-mcp harness, so they can decide if injecting input without taking over their real controls is worth pursuing. This review reads Godot 4.7.2-stable, Apple's documentation, the godot-mcp fork and urchin. The review itself ran no experiment and opened no window. E2 was run afterwards, and section 8 has its results. Nothing in urchin or the fork changed except this file.

Outcome: the fork's `run_project` and `run_scene` now take `embedded: true` (fork commit `9cbe791`, section 6 step 1), and every in-game check in wave 5 ran that way.

Every claim carries a tag:

- [source]: read in code or documentation. The link or path is given.
- [measured]: a log or command output from this Mac. The path or command is given.
- [inferred]: reasoned from the cited sources. The reasoning is given.
- [guess]: no source read here settles it. Section 7 names the experiment that does.

## Answer

**The window does not need focus.** [source] No step between `Input.parse_input_event()` and `_input`, the GUI or `_unhandled_input` checks window focus or app activation, for keys, mouse buttons, motion, hover or `InputEventAction` (section 1.1). [measured] An injected key reached the game while it was minimized (`M/final.log:13-14`). Mouse and GUI events while unfocused have not been measured (E6).

**A separate screen only decides whether Godot keeps drawing.** Input never looks at where the window is.

- Another Space: [source] a window on another Space counts as occluded, and Godot skips rendering when no window is visible, so screenshots fail (section 2). [measured] Game logic and the harness keep running with an occluded window (`M/final.log:7-11`).
- A second display: [inferred] the game keeps drawing while it sits on that display's current Space and is not fully covered, whichever display Julian works on (section 2.2). [measured] This Mac has only the built-in display attached today (`system_profiler SPDisplaysDataType`).
- A virtual display: [source] Apple publishes no API that creates one (section 2.2).

**A separate screen stops neither of the two takeovers.**

- The cursor. [source] `warpMouse: true` ends in `CGWarpMouseCursorPosition`, which takes one global point, so the real cursor jumps to the game's display (section 4.2). urchin needs it only because of `scripts/battle/battle_scene.gd:167`.
- The launch. [source] Godot activates itself every time it shows its main window, on any display, and `display/window/size/no_focus` does not change that (section 5).

**It is worth pursuing, but not by moving the window.** The options:

| Option | Real cursor left alone | No focus grab at launch | Renders while hidden | Cost | Evidence |
|---|---|---|---|---|---|
| Second physical display | No, a warp follows the window | No | Only on that display's current Space | A display, none attached today | [inferred], E5 |
| Another Space | No | No | No | None | [source] |
| Keep any part of the window uncovered | Not applicable | No | Yes | None | [source] |
| Read the pointer from input events at `battle_scene.gd:167` | Yes, urchin stops needing a warp | No | Not applicable | One call site in urchin | [inferred] |
| `RenderingServer.force_draw(false)` before reading the texture | Not applicable | No | Yes, for screenshots | The harness screenshot path | [inferred], E1 |
| `DisplayServer.register_additional_output()` | Not applicable | No | Only with 1 s Metal stalls or a window that stops presenting (section 3.2) | One call | [inferred], E3 |
| `--embedded` launch flag | Yes | Yes | Yes | One launch flag, in an undocumented editor mode, with no window to watch | [measured], E2 (section 8) |

Section 6 gives the order. In short: E2 passed, so one launch flag removes both takeovers with no change to urchin. If that mode breaks on an engine upgrade, change the one urchin call site and add the `force_draw(false)` path once E1 passes. The launch focus grab then stays, once per run.

[source] `DisplayServerMacOS::_dispatch_input_event` sends the event to the window named by `window_id`, or to every window for events that carry none, and redirects keys to an open native popup ([display_server_macos.mm:459-502](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L459-L502)). [source] `Viewport::push_input` has four early exits: `disable_input` ([viewport.cpp:3494](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3494)), an editor-only check ([:3498](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3498)), an event that an embedded subwindow takes ([:3526-3529](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3526-L3529)), and `_can_consume_input_events` ([:3531](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3531)), which is false only while an exclusive child window is open ([window.cpp:2000-2002](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/window.cpp#L2000-L2002)). It updates hover for mouse events ([viewport.cpp:3521-3524](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3521-L3524)), then calls `_input` ([:3537](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3537)), the GUI ([:3542](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3542)) and unhandled input ([:3549](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3549)).

### 1.2 What a real focus loss does to an injected sequence

- [source] When the window loses key status, `windowDidResignKey` calls `release_pressed_events` and sends `WINDOW_EVENT_FOCUS_OUT` ([godot_window_delegate.mm:339-355](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_window_delegate.mm#L339-L355)). `windowDidMiniaturize` does the same ([:357-369](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_window_delegate.mm#L357-L369)), and `windowDidMove` also calls `release_pressed_events` ([:302](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_window_delegate.mm#L302)).
- [source] `Input::release_pressed_events` returns at once while `application_focused` is true ([input.cpp:1600-1604](https://github.com/godotengine/godot/blob/4.7.2-stable/core/input/input.cpp#L1600-L1604)), and that flag starts true ([input.h:130](https://github.com/godotengine/godot/blob/4.7.2-stable/core/input/input.h#L130)). It turns false when AppKit reports the app resigned active ([godot_application_delegate.mm:221-229](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_application_delegate.mm#L221-L229), [scene_tree.cpp:934-943](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/scene_tree.cpp#L934-L943)), and that notification runs the release.
- [source] The release clears `keys_pressed`, `physical_keys_pressed` and `key_label_pressed`, and calls `action_release` on pressed actions held by a non-joypad event ([input.cpp:1608-1645](https://github.com/godotengine/godot/blob/4.7.2-stable/core/input/input.cpp#L1608-L1645)). It leaves the mouse button mask alone.
- [inferred] A held injected key or `action` stops reading as pressed through `Input.is_*`, while `_input` still sees the press and the later release, because the release edits state and dispatches no event. urchin is not exposed: [source] `rg 'Input\.is_' scripts` finds no polling.
- [source] `WINDOW_EVENT_FOCUS_OUT` becomes `NOTIFICATION_WM_WINDOW_FOCUS_OUT` ([window.cpp:898-905](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/window.cpp#L898-L905)). The viewport then cancels tooltips, drops physics mouseover and calls `_drop_mouse_focus`, keeping hover on purpose ([viewport.cpp:760-768](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L760-L768)). `_drop_mouse_focus` sends an internal button release to the pressed Control ([:2752-2774](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L2752-L2774)).
- [inferred] A real focus loss during an injected press ends it early. In its default release action mode, `BaseButton` emits `pressed` on any release while `press_attempt` and `pressing_inside` hold ([base_button.cpp:252-274](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/gui/base_button.cpp#L252-L274)), so the button fires at the moment of focus loss, and the harness's own release later finds no mouse focus and is dropped ([viewport.cpp:2019-2022](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L2019-L2022)). A drag in flight loses its Control the same way. The window for this is small: the harness holds a click for 50 ms and spreads a drag over about 100 ms (`F/src/scripts/mcp_harness.gd:35-39`).
- [source] A real pointer exit arrives through `mouseExited:` ([godot_content_view.mm:620-629](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_content_view.mm#L620-L629)) and `WINDOW_EVENT_MOUSE_EXIT`, which flushes buffered input and calls `_mouse_leave_viewport` ([window.cpp:862-880](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/window.cpp#L862-L880)). That drops hover and marks the mouse as outside the viewport, and keeps mouse focus on purpose ([viewport.cpp:3433-3444](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3433-L3444), [:752-758](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L752-L758)).
- [inferred] A click in flight survives a pointer exit, because `BaseButton` needs hovering only on the press ([base_button.cpp:243](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/gui/base_button.cpp#L243)), and the next injected motion rebuilds hover ([window.cpp:3310-3312](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/window.cpp#L3310-L3312)).
- [inferred] The focus-loss paths above fire on a change of key status or activation, so they do not run again while the game stays unfocused. Launch activation (section 5) gives the game focus once, so Julian's first click elsewhere triggers them once.

### 1.3 Real input reaching an unfocused game

- [source] `updateTrackingAreas` asks for enter, exit and cursor-update messages, active only while the view is first responder, and does not ask for `NSTrackingMouseMoved` ([godot_content_view.mm:663-673](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_content_view.mm#L663-L673), [Apple: activeWhenFirstResponder](https://developer.apple.com/documentation/appkit/nstrackingarea/options-swift.struct/activewhenfirstresponder), `AppKit/NSTrackingArea.h:26`).
- [source] The window turns on mouse-moved events ([display_server_macos.mm:156](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L156)), and Apple says those go to the first responder, not the view under the pointer ([Event Architecture](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/EventArchitecture/EventArchitecture.html)).
- [guess] Apple's pages do not say whether a view in a non-key window of an inactive app counts for either rule, so nothing read here settles whether Julian's pointer passing over an unfocused game reaches `mouseMoved:` or `mouseEntered:`. E4 settles it.
- [source] Key events go to the key window ([Event Architecture](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/EventArchitecture/EventArchitecture.html)), so Julian's typing does not reach an unfocused game.
- [source] Real clicks do reach it. The content view returns YES from `acceptsFirstMouse:` ([godot_content_view.mm:79-81](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_content_view.mm#L79-L81)), which is Apple's click-through: the first click in an inactive window is delivered and also activates it ([acceptsFirstMouse(for:)](https://developer.apple.com/documentation/appkit/nsview/acceptsfirstmouse(for:))).
- [guess] Scroll and trackpad gestures: the view handles them ([godot_content_view.mm:890](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_content_view.mm#L890), [:644](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_content_view.mm#L644)), and the pages read do not say how they route to an inactive window. E4 settles it.
- [source] Two engine paths read the real cursor whatever the focus state. Physics picking builds a passive hover event from `get_mouse_position()` when the mouse counts as inside the viewport, no Control is hovered and no mouse event is queued ([viewport.cpp:790](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L790), [:825-856](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L825-L856)). `Window::update_mouse_cursor_state` pushes an internal motion event at the real cursor position ([window.cpp:935-950](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/window.cpp#L935-L950)), on a scene change ([scene_tree.cpp:1692](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/scene_tree.cpp#L1692)), at drag end ([viewport.cpp:2459](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L2459)) and on a cursor shape change ([control.cpp:3530](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/gui/control.cpp#L3530)).
- [inferred] `battle_scene.gd:167` is urchin's only direct read of the OS pointer, but it is not the engine's only one. urchin takes little harm: the orb's `mouse_entered` on its Area2D only prints (`scripts/ui/orb_base.gd:58-59`, `scenes/orb.tscn:148`), its clicks go through a Control (`scripts/ui/orb_base.gd:20-28`), and after a scene change hover follows the real cursor only until the next injected motion, which every harness `click` sends first.

## 2. Separate screen

### 2.1 What makes the window drawable

- [source] `window_can_draw` returns the window's `is_visible`, and `can_any_window_draw` is true when any window has it ([display_server_macos.mm:2709-2722](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L2709-L2722)). It starts true ([display_server_macos.h:138](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.h#L138)).
- [source] Two places write it, `windowDidChangeOcclusionState` and `windowDidDeminiaturize`, both as occlusion-visible and `isVisible` ([godot_window_delegate.mm:387-393](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_window_delegate.mm#L387-L393), [:377](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_window_delegate.mm#L377)). [PR 83096](https://github.com/godotengine/godot/pull/83096) replaced an `isOnActiveSpace` check with this.
- [source] Apple defines the visible state as at least part of the window being visible ([occlusionState](https://developer.apple.com/documentation/appkit/nswindow/occlusionstate-swift.property)). AppKit's 10.9 notes, section "Application and Window Occlusion", list what occludes a window: complete cover by opaque windows including the title bar, being ordered off screen, being minimized to the Dock, or being on another Space. Partial cover counts as visible ([AppKit release notes](https://developer.apple.com/library/archive/releasenotes/AppKit/RN-AppKitOlderNotes/index.html)).
- [measured] Fully covered by another window: `window_can_draw` false, mode windowed, `Engine.get_frames_drawn()` flat at 457 for 23.7 s, process frames still running at 145 per second (`M/old-covered2.log:21-114`). Minimized gives the same result with mode 1 (`M/final.log:7`).
- [source] When the window cannot draw, the frame delay sleeps the low-processor interval, which defaults to 6900 microseconds ([os.cpp:721-723](https://github.com/godotengine/godot/blob/4.7.2-stable/core/os/os.cpp#L721-L723), [main.cpp:2264-2265](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L2264-L2265)). [inferred] That interval allows 144.9 frames per second, which matches the measured 145, so the sleep is the cap. The matching number is the only evidence.
- [source] App Nap skips apps that hold an IOKit power assertion ([Apple: Extend App Nap](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/AppNap.html)), and Godot takes one by default ([display_server_macos_base.mm:742](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos_base.mm#L742), [:474](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos_base.mm#L474), [ProjectSettings.xml:969](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/ProjectSettings.xml#L969)). [inferred] A hidden game is not napped, and the 145 per second above agrees.

### 2.3 Placing the window

- [source] The fork puts game arguments after `--`, so `args` cannot carry engine flags (`F/src/index.ts:1640-1655`). `--screen` and `--position` need a new launch option.
- [source] `--screen N` picks the screen and `--position X,Y` the point ([main.cpp:1469-1476](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L1469-L1476), [:1481-1503](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L1481-L1503)). With no position the window is centered on that screen ([display_server_macos.mm:3880-3886](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L3880-L3886)), and the position is clamped to the screen's usable area ([:120-128](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L120-L128)).
- [source] `display/window/size/initial_screen` applies only with the "Other Screen Center" position type ([main.cpp:2741-2743](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L2741-L2743), [ProjectSettings.xml:1032-1033](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/ProjectSettings.xml#L1032-L1033)), so it means changing the project.
- [source] `DisplayServer.window_set_current_screen` works at runtime ([display_server_macos.mm:1860-1890](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L1860-L1890)). [inferred] The harness can call it from `_initialize` with no launcher change, but `show_window` has already run by then ([main.cpp:3459](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L3459)), so the window opens on the primary display first.
- [source] Godot has no way to pick a Space: it only sets full-screen collection behaviors ([display_server_macos.mm:153](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L153)). The per-app "Assign To" option in the Dock is the user-level route, its All Desktops choice puts the app on every Space, and by default activating an app switches to a Space holding its windows ([Work in multiple spaces](https://support.apple.com/guide/mac-help/work-in-multiple-spaces-mh14112/mac), [Desktop & Dock settings](https://support.apple.com/guide/mac-help/change-desktop-dock-settings-mchlp1119/27/mac/27)). [inferred] Launching the game assigned to another Space pulls Julian to that Space when Godot activates itself.

## 3. Does the window need to be visible at all?

Short answer: no, for screenshots. Both leads exist in the source. `register_additional_output()` is unusable on a covered Metal window, and `force_draw(false)` holds up on reading.

### 3.1 The gate

- [source] `wants_present` is true when any window can draw or an additional output is registered, and the render loop is on. A frame draws when `wants_present` is true or the RenderingDevice has pending resources, and only these draws count toward `frames_drawn` ([main.cpp:5081-5097](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L5081-L5097)).

### 3.2 `register_additional_output()`: real, and the wrong tool on Metal

- [source] It exists and scripts can call it ([display_server.cpp:1723-1725](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/display/display_server.cpp#L1723-L1725)). The class docs give this exact purpose ([DisplayServer.xml:1739-1745](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/DisplayServer.xml#L1739-L1745)), and [PR 94412](https://github.com/godotengine/godot/pull/94412) added it so XR keeps rendering with no visible window.
- [source] It makes frames run with present on. `draw_viewports(true)` blits to the window ([renderer_viewport.cpp:980-984](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_viewport.cpp#L980-L984)), which prepares the swapchain ([renderer_compositor_rd.cpp:43](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_rd/renderer_compositor_rd.cpp#L43), [rendering_device.cpp:5399](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/rendering_device.cpp#L5399)), which calls `nextDrawable` ([rendering_context_driver_metal.cpp:192](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/metal/rendering_context_driver_metal.cpp#L192)).
- [inferred] On a covered window each frame then hits the wait in section 3.4. If a drawable comes back after the wait, the game renders at about one frame per second. If nil comes back, three frames use up the swapchain slots and the window stops presenting for the rest of the run. Neither outcome is usable. E3 tells them apart, at low priority.

### 3.3 `RenderingServer.force_draw(false)`: holds up on reading

- [source] `force_draw(swap_buffers, frame_step)` binds to `RenderingServer::draw` ([rendering_server.cpp:3573](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/rendering_server.cpp#L3573), [RenderingServer.xml:1614-1620](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/RenderingServer.xml#L1614-L1620)), which has no window check ([rendering_server_default.cpp:443-453](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/rendering_server_default.cpp#L443-L453)).
- [source] With `false`, `draw_viewports` still renders each viewport into its render target ([renderer_viewport.cpp:929](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_viewport.cpp#L929)) and skips the blit ([:980](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_viewport.cpp#L980)). `end_frame(false)` submits with no present ([renderer_compositor_rd.cpp:135-137](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_rd/renderer_compositor_rd.cpp#L135-L137), [rendering_device.cpp:8189](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/rendering_device.cpp#L8189)). The engine takes this path itself when it has pending resources and no window to present to ([main.cpp:5085-5093](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L5085-L5093)).
- [source] The root viewport qualifies: it is attached to the screen, and the visibility test looks at the rect and the size, not the window ([renderer_viewport.cpp:827](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_viewport.cpp#L827), [:851](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_viewport.cpp#L851)). None of `renderer_viewport.cpp`, `rendering_server_default.cpp`, `renderer_compositor_rd.cpp` or `rendering_device.cpp` calls `window_can_draw` or `can_any_window_draw`.
- [source] `root.get_texture().get_image()` reads the render target and flushes the GPU first ([viewport.cpp:197-203](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L197-L203), [texture_storage.cpp:1882](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_rd/storage_rd/texture_storage.cpp#L1882), [rendering_device.cpp:2737](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/rendering_device.cpp#L2737)).
- [inferred] So after `force_draw(false)` the texture is current and valid, with no swapchain involved. E1 confirms it.
- [source] `force_draw` does not raise `Engine.get_frames_drawn()`, because only `Main::iteration` does ([main.cpp:5090](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L5090), [:5094](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L5094)). The harness's guard and frame wait are the two lines in the way (`F/src/scripts/mcp_harness.gd:211`, `:213`).

### 3.4 The Metal swapchain problem

- [source] `nextDrawable` waits up to one second when no drawable is free and then returns nil ([Apple: nextDrawable()](https://developer.apple.com/documentation/quartzcore/cametallayer/nextdrawable())), and Godot leaves that timeout on ([rendering_context_driver_metal.cpp:109](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/metal/rendering_context_driver_metal.cpp#L109)).
- [source] [Issue 124667](https://github.com/godotengine/godot/issues/124667), against this exact build, reports one frame of about 1 s each time another window covers the game, with a stack sample ending in `nextDrawable`. It attributes the wait to Core Animation withholding drawables from an occluded layer. It is open, labelled "needs testing", and no maintainer has confirmed it.
- [measured] Julian's log has the same shape: the interval that first shows `can_draw=false` took 1077 ms against the usual 250 ms and held only 9 frames (`M/old-covered2.log:20-21`). [inferred] That is the same stall, from the matching timing and the issue's stack. The log alone shows only the gap.
- [inferred] `window_can_draw` going false is what protects later frames, so anything that forces present while covered goes back into that wait.
- [inferred] A nil drawable is never handed back. `acquire_next_frame_buffer` raises `count` before asking and returns on nil without lowering it ([rendering_context_driver_metal.cpp:182-193](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/metal/rendering_context_driver_metal.cpp#L182-L193)), `present` runs only for swap chains queued after a good acquire ([rendering_device.cpp:5413-5422](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/rendering_device.cpp#L5413-L5422)), and the only other writes to `count` are the decrements after a present. After as many nil results as swapchain images, 3 by default ([ProjectSettings.xml:3393](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/ProjectSettings.xml#L3393)), acquire fails at once and the blit is skipped with no error ([renderer_compositor_rd.cpp:43-47](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_rd/renderer_compositor_rd.cpp#L43-L47)). No log shows whether nil is what comes back.
- [source] `GODOT_MTL_OFF_SCREEN=1` selects a surface that takes a real drawable at most once a second ([rendering_context_driver_metal.cpp:399-403](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/metal/rendering_context_driver_metal.cpp#L399-L403), [:346-355](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/metal/rendering_context_driver_metal.cpp#L346-L355)). [inferred] It does nothing for `force_draw(false)`, which never acquires one.

## 4. The cursor

### 4.1 What reads the OS cursor

- [source] `get_global_mouse_position` applies the inverse canvas transform to `Viewport.get_mouse_position` ([canvas_item.cpp:1372-1375](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/canvas_item.cpp#L1372-L1375)).
- [source] `Viewport::get_mouse_position` has three branches ([viewport.cpp:1483-1500](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L1483-L1500)). A viewport whose section root is not the scene root uses `gui.last_mouse_pos`, the last event position. With `FEATURE_MOUSE` it converts `DisplayServer.mouse_get_position()`, and macOS has that feature ([display_server_macos.mm:830](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L830)). Otherwise it reads `Input`'s stored position, which injected events update ([input.cpp:845-848](https://github.com/godotengine/godot/blob/4.7.2-stable/core/input/input.cpp#L845-L848), [:868-871](https://github.com/godotengine/godot/blob/4.7.2-stable/core/input/input.cpp#L868-L871)) and scripts cannot read directly ([:188-193](https://github.com/godotengine/godot/blob/4.7.2-stable/core/input/input.cpp#L188-L193)).
- [source] macOS `mouse_get_position` reads `[NSEvent mouseLocation]` ([display_server_macos.mm:1381-1398](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L1381-L1398)), which Apple defines as the current screen position regardless of pending events ([mouseLocation](https://developer.apple.com/documentation/appkit/nsevent/mouselocation)).
- [inferred] So the root viewport ignores injected events for this read. Each frame `battle_scene.gd:167` tests the real cursor against the ring. Outside it, a 0.15 s timer and a 0.67 s fade close the menu (`scripts/battle/battle_scene.gd:177-186`, `scenes/battle_scene.tscn:93-95`, `scripts/battle/battle_scene.gd:67`), which is why an attack click needs the warp.

### 4.2 Warp, and why a separate screen does not help

- [source] `root.warp_mouse` goes through `Input::warp_mouse` and the display server to `CGWarpMouseCursorPosition` ([viewport.cpp:1502-1507](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L1502-L1507), [input.cpp:1381-1383](https://github.com/godotengine/godot/blob/4.7.2-stable/core/input/input.cpp#L1381-L1383), [display_server.cpp:2080-2082](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/display/display_server.cpp#L2080-L2082), [display_server_macos.mm:1351-1379](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L1351-L1379)).
- [source] Apple: the call moves the cursor without generating events ([CGWarpMouseCursorPosition](https://developer.apple.com/documentation/coregraphics/cgwarpmousecursorposition(_:))), taking one point in global display coordinates (`CoreGraphics/CGRemoteOperation.h:219-222`).
- [inferred] It takes no window, display or process, so warping to a window on a second display moves the real cursor to that display. A separate screen makes the jump longer, not absent.

### 4.3 Ways not to touch the real cursor

1. Read the pointer from input events at the one call site. [source] `_update_radial_menu_fade` already takes a point, split out so a test can pass one (`scripts/battle/battle_scene.gd:170-177`). `_input` events carry viewport coordinates ([viewport.cpp:1467-1481](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L1467-L1481)), and the ring is under a Node2D in the default canvas (`scripts/battle/battle_scene.gd:442`, `scenes/battle_scene.tscn:91`). [inferred] The last `InputEventMouseMotion.position` then matches what the current read returns, and both real and injected motion supply it. If E4 shows real motion reaches an unfocused game, Julian's pointer passing over the window feeds the same value. One change for real players: [inferred] leaving the window sends no more motion, so the fade no longer starts when the pointer leaves from on top of the ring, and `NOTIFICATION_WM_MOUSE_EXIT` covers that case.
2. `Viewport.gui_get_hovered_control()`. [source] It returns the control from `gui.mouse_over` ([viewport.cpp:3800-3803](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3800-L3803)), which event positions update ([:3331-3375](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L3331-L3375)). urchin's hit test compares the rects of the unit's `hit_button` and the orbs, all of them `Button`s (`scripts/battle/battle_scene.gd:419`, `:590-599`, `scripts/battle/unit_overlay.gd:20`). [inferred] Comparing the hovered Control against those buttons gives the same answer while no other Control sits on top of them, with more rewriting than option 1.
3. The SubViewport branch. [source] Only a SubViewport outside a SubViewportContainer is its own section root ([viewport.cpp:5744-5750](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/viewport.cpp#L5744-L5750)). [inferred] Using it means re-parenting the game under one and pushing input into it, which changes the tree under test. Not worth it.
4. An embedded Window. The lead is wrong. [source] An embedded `Window` resolves to its embedder's section root, which is the scene root ([window.cpp:3278-3288](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/main/window.cpp#L3278-L3288)), so it reads the OS cursor.
5. Posting CGEvents to the process. [source] `CGEventPostToPid` posts into one application's event stream (`CoreGraphics/CGEvent.h:357-372`, [Apple](https://developer.apple.com/documentation/coregraphics/cgevent/posttopid(_:))). [inferred] It does not help. `parse_input_event` already delivers events, and the game's read comes from `NSEvent.mouseLocation`. If a posted event moves the cursor, the takeover is back. If it does not, the read does not change.
6. Warp and restore. [inferred] This fails across separate `simulate_input` calls. `battle_scene.gd:167` reads every frame while the menu is open, so a restored cursor closes the menu 0.82 s later, the 0.15 s timer plus the 0.67 s fade. The real cursor still jumps during the warp.
7. `--embedded`, which reaches the third branch. See section 4.4.

### 4.4 `--embedded`

This is the only path found that addresses the cursor, the launch focus grab and hidden rendering at once.

- [source] The editor passes `--wid` and `--embedded` when it embeds the running game ([game_view_plugin.cpp:1321-1325](https://github.com/godotengine/godot/blob/4.7.2-stable/editor/run/game_view_plugin.cpp#L1321-L1325)). ## 5. Focus stealing at launch

### 5.1 Where it happens

1. [source] `OS_MacOS_NSApp` sets the regular activation policy ([os_macos.mm:1205](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/os_macos.mm#L1205)). `Main::setup` runs from `applicationDidFinishLaunching` ([godot_application_delegate.mm:142-144](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_application_delegate.mm#L142-L144), [os_macos.mm:1111-1114](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/os_macos.mm#L1111-L1114)).
2. [source] Setup shows the main window ([main.cpp:3458-3460](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L3458-L3460)), before the `-s` script's main loop initializes ([os_macos.mm:1127](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/os_macos.mm#L1127)).
3. [source] `show_window` calls `[GodotApp activateApplication]` for the main window, with no `no_focus` check, and then `makeKeyAndOrderFront:`, or `orderFront:` when `no_focus` is set ([display_server_macos.mm:1715-1737](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L1715-L1737)).
4. [source] `activateApplication` calls `activateIgnoringOtherApps:YES`. When any standard stream is a TTY, or the bundle id does not match `__CFBundleIdentifier`, it also schedules a three-step hop through SystemUIServer, `TransformProcessType` and a second activation ([godot_application.mm:59-75](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_application.mm#L59-L75), [:172-194](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_application.mm#L172-L194)).
5. [measured] This session's `__CFBundleIdentifier` is `com.anthropic.claudefordesktop` and `/Applications/Godot.app` has bundle id `org.godotengine.godot` (`plutil -extract CFBundleIdentifier raw`). [source] The fork copies `process.env` to the child (`F/src/index.ts:1642`). [inferred] The hop therefore runs on every harness launch from the Claude desktop app.
6. [source] Apple says that with YES the app activates regardless of others. Its documentation marks the call deprecated at macOS 27.0 and directs callers to `activate()`, which is only a request ([activate(ignoringOtherApps:)](https://developer.apple.com/documentation/appkit/nsapplication/activate(ignoringotherapps:)), [activate()](https://developer.apple.com/documentation/appkit/nsapplication/activate())). [guess] macOS 27.2 still honors the old call. No log here shows it. E8 settles it.

### 5.2 What would stop it

- `display/window/size/no_focus`: it does not stop it. [source] The flag reaches the window before `show_window` ([main.cpp:2723-2725](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L2723-L2725), [display_server_macos.mm:3892](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L3892)) and blocks key and main status ([godot_window.mm:60-80](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/godot_window.mm#L60-L80)), but `activateApplication` still runs. [inferred] Julian's app still loses activation and no window is key, so their typing goes nowhere, which is worse than today.
- `WINDOW_FLAG_NO_FOCUS` from the harness: [inferred] too late, because `_initialize` runs after `show_window` (5.1 step 2).
- Background launch: [source] `open -g` keeps LaunchServices from bringing the app forward (`man open`). [inferred] Godot activates itself afterward anyway. `open` also starts the app through LaunchServices instead of as a child process, so the stdio pipes the fork reads (`F/src/index.ts:1657`) do not connect to it.
- `LSUIElement` or `LSBackgroundOnly`: [source] Godot sets the regular activation policy at runtime, unconditionally ([os_macos.mm:1205](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/os_macos.mm#L1205)). [inferred] That replaces whatever the Info.plist asked for.
- `__CFBundleIdentifier=org.godotengine.godot` in the child's environment: [inferred] skips the SystemUIServer hop and leaves the plain activation.
- `--embedded`: [source] the only route found (section 4.4).

### 5.3 What focus changes for the harness

- [inferred] Nothing the harness does depends on focus. It does not call `has_focus`, and a warp falls back to the main window when nothing has been focused ([display_server_macos.mm:1355-1358](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/macos/display_server_macos.mm#L1355-L1358)).
- [inferred] A game that never activates never gets `applicationDidResignActive:`, so `application_focused` stays at its initial true and the release path in 1.2 does not run.
- [inferred] The launch costs Julian one interruption per `run_project`, not one per input.

## 6. Recommendation

Worth pursuing. The goal, driving the game without taking over the real controls, is reachable, and neither takeover is related to which screen the window is on.

Smallest path:

1. E2 passed, so add one launch option to the fork that places `--embedded` before `--`. That removes the cursor warp, the focus grab and the hidden-window problem, with no change to urchin. Accept that it depends on an editor-private mode and re-check it on engine upgrades.
2. If the mode breaks on a later engine, make two independent small changes. Change the one call site at `scripts/battle/battle_scene.gd:167` to use the pointer from input events, so urchin stops needing `warpMouse`. Run E1, and if it passes, have the harness use `force_draw(false)` when `window_can_draw()` is false, so screenshots work wherever the window is. The launch focus grab stays, once per run, and the game needs no focus after it.
3. Today, at no cost: keep any part of the game window uncovered, and the engine keeps drawing.

Do not spend effort on:

- A second display or a virtual display for this purpose. It only keeps the window visible, and the option above does that for free.
- A separate Space, which stops drawing.
- `no_focus`, a background launch or Info.plist keys.
- `register_additional_output()` on Metal.
- Posting CGEvents.
